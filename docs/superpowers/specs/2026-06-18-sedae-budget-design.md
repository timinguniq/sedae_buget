# 세대 가계부 (Sedae Budget) — 설계안

- **작성일**: 2026-06-18
- **상태**: 승인됨 (설계 확정, 구현 계획 작성 대기)
- **한 줄 정의**: 내 지출을 **같은 연령 세대(또래) 평균과 비교**해주는 가계부 앱

---

## 1. 목표

연령 세대(또래) 가계부. 사용자가 자신의 지출을 입력하면, **같은 세대의 평균 소비와 비교**해 "내 또래는 이만큼 쓰는데 나는?"라는 인사이트를 제공한다.

- **핵심 가치**: 단순 기록이 아니라 *또래 대비 내 소비 위치*를 보여주는 비교 인사이트
- **전략**: **로컬 우선**(개인 가계부로 즉시 동작) → **서버 연동**(세대 비교 활성화). 클라이언트를 먼저 만들고 초기에는 로컬에 저장하다가, 서버를 구축한 뒤 API로 연결한다.

---

## 2. 핵심 결정사항

브레인스토밍에서 확정한 방향. 이후 모든 설계는 이 결정을 전제로 한다.

| 항목 | 결정 | 비고 |
|---|---|---|
| "세대"의 의미 | **연령 세대(또래 비교)** | 20·30·40대 등 같은 연령 집단 평균과 비교 |
| 비교 기준 데이터 | **앱 사용자 익명 집계** | 실사용자 지출을 세대별로 집계 (콜드 스타트 리스크 존재) |
| 백엔드 | **커스텀 REST 백엔드** | 스캐폴드의 dio 클라이언트·`app_endpoint` 활용 |
| 지출 입력 방식 | **수동 입력 (MVP)** | 자동 입력(문자/마이데이터)은 후속 검토 |
| 신원/계정 | **소셜 로그인 필수** (Apple/Google/Kakao) | 온보딩에서 출생연도·성별 수집 |
| 개발 프로세스 | **클라이언트 우선 + 로컬→서버** | 로컬 저장으로 시작, 서버 구축 후 API 연결 |

## 3. 단계별 로드맵

### Phase 0 — 기반 정비
- 기존 Flutter 스캐폴드(클린 아키텍처: presentation/domain/data/entity/core/theme) 위에 `domain`·`data` 레이어 규약 확정
- 표준 카테고리(§6) 정의 및 시드
- 환경/빌드 정리 (`.env`, 라우팅, 테마는 이미 갖춰짐)

### Phase 1 — 로컬 가계부 (동작하는 MVP, 로그인 불필요)
- 지출(+수입 선택) **수동 입력 CRUD**
- 표준 카테고리 선택
- **월별 보기 / 카테고리별 합계** 집계 화면
- 로컬 영속화 (SQLite — `drift` 또는 `sqflite`, Phase 1 착수 시 확정)
- **Repository 인터페이스 + `LocalDataSource`** 로 추후 원격 스왑 대비
- 산출물: 인터넷 없이도 쓸 수 있는 개인 가계부

### Phase 2 — 서버 + 세대 비교 (Cloud MVP)
- 커스텀 REST 백엔드 + DB 구축
- 소셜 로그인(Apple/Google/Kakao), 온보딩에서 출생연도·성별
- 로컬 데이터 → 서버 **동기화(업로드/머지)**
- 세대별 **익명 집계** (배치/온디맨드)
- **"내 소비 vs 세대 평균" 비교 화면**
- 산출물: 세대 비교 인사이트가 동작하는 앱

### Phase 3 — 고도화 (후속)
- 인사이트/리포트, 예산·목표 설정
- 자동 입력(문자 파싱 / 마이데이터·오픈뱅킹) 규제 검토 후 도입
- 다국어, 추가 비교 축(성별·지역 등)

## 4. 클라이언트 아키텍처 (기존 스캐폴드 준수)

```
presentation  (page / widget / route / service)   ← Riverpod
      ↓
domain        (entity / repository interface / usecase)
      ↓
data          (repository impl / datasource: local·remote / dto)
      ↓
core, theme   (공통 유틸·http·DI·테마)
```

- **상태관리**: Riverpod (스캐폴드 채택). 테마는 Provider 유지.
- **데이터 흐름**: UI → Riverpod provider → UseCase → Repository(interface) → DataSource
- **전환 핵심**: Repository 인터페이스는 `domain`에 고정한다. Phase 1은 `LocalDataSource` 구현만 두고, Phase 2에서 `RemoteDataSource` + 동기화 계층을 추가한다. **UI와 도메인 코드는 전환 시에도 그대로 유지**되는 것이 목표.

---

## 5. 데이터 모델 (도메인)

- **Profile**: `id`, `birthYear`, `generation`(파생), `gender`, `createdAt`
  - Phase 1: 로컬 프로필(또는 미설정) / Phase 2: 서버 계정에 귀속
- **Transaction**: `id`, `amount`, `categoryId`, `date`, `memo`, `type`(지출/수입), `createdAt`, `syncStatus`
- **Category**: `id`, `name`, `group`, `icon` — **표준 고정 세트**(집계 비교 가능하도록)
- **GenerationStat** (서버 집계 산출물): `generation` × `categoryId` × `period`(월) → `avgAmount`, `medianAmount`, `sampleSize`

---

## 6. 표준 카테고리 (집계 비교의 전제)

세대 간 비교가 의미 있으려면 카테고리가 통일돼야 한다. **통계청 가계동향조사 12대 분류**를 기준으로 한다:

1. 식료품·비주류음료
2. 주류·담배
3. 의류·신발
4. 주거·수도·광열
5. 가정용품·가사서비스
6. 보건
7. 교통
8. 통신
9. 오락·문화
10. 교육
11. 음식·숙박(외식)
12. 기타 상품·서비스

- 사용자가 만든 자유 카테고리는 위 표준 분류에 **매핑**하여 집계한다(집계는 항상 표준 기준).

---

## 7. 백엔드 (Phase 2)

- **방식**: REST API (스캐폴드의 dio·`app_endpoint` 활용). **OpenAPI 계약 문서화** 우선.
- **엔드포인트 초안**:
  - `POST /auth/social` — 소셜 토큰 검증 → 앱 토큰 발급
  - `GET /me`, `PUT /me` — 프로필(출생연도·성별 등)
  - `POST /transactions` — 거래 배치 업로드/동기화
  - `GET /transactions` — 내 거래 조회
  - `GET /stats/generation?period=YYYY-MM` — 내 세대 비교 데이터
- **집계**: 주기적 배치로 `generation × category × month` 평균·중앙값·표본수 산출
- **프라이버시**:
  - 개인 원자료는 익명 처리, 집계만 노출
  - 표본 수가 임계치(k) 미만인 세대×카테고리는 비교 **미노출** (k-익명성)
  - 데이터 수집·이용 동의 및 약관 필요
- **스택**: Phase 2 착수 시 확정(예: NestJS / FastAPI / Spring 등). 계약(OpenAPI)을 먼저 고정하고 스택은 그 위에서 선택.

---

## 8. 동기화 전략 (local → server 전환의 핵심)

- Phase 1 데이터 모델에 `syncStatus` 여지를 두어 추후 동기화에 대비
- Phase 2 진입 시: 로그인 후 로컬 데이터를 일괄 업로드
- 도입 이후 모델: **"서버 = source of truth, 로컬 = 캐시"** 로 단순화
- 충돌 정책(동일 거래 중복·수정 충돌)을 Phase 2 설계 시 명시

---

## 9. 세대 구간 정의

- 출생연도 기반으로 세대 버킷을 정의 (예: 10년 단위 또는 명명 세대)
- 비교 단위(예: "30대" vs "1990–1994년생")는 Phase 2 착수 시 확정
- 집계·표시 모두 동일한 버킷 정의를 사용

---

## 10. 테스트 전략

- **도메인**: UseCase·Repository 단위 테스트 (fake `LocalDataSource`)
- **UI**: 주요 화면 위젯 테스트 (입력, 월별 보기, 비교)
- **백엔드(Phase 2)**: 집계 로직 단위 테스트, 표본 부족 등 엣지 케이스
- **비교 정확도**: 세대 버킷 분류·평균/중앙값 계산 검증

---

## 11. 리스크 / 미해결 과제

- **콜드 스타트**: 초기 사용자가 적으면 세대 비교 표본이 부족해 부정확 → 출시 초기 "표본 모이는 중" UX, 또는 공공 통계 시드 보조를 후속 검토
- **로그인 도입 시점**: 로컬-우선 전략이라 소셜 로그인은 Phase 2에서 도입 → **Phase 1에서 쌓인 로컬 데이터를 어떻게 계정에 귀속**시킬지 Phase 2 설계에서 정의 필요
- **자동 입력**: 문자 파싱(권한·정확도·iOS 제약), 마이데이터(라이선스·사업자 등록)는 규제 부담이 커 Phase 3에서 별도 검토
